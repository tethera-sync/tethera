# Implementation Status

This document separates implemented behaviour from planned behaviour so the product does not imply that unfinished sync features are protecting data.

## Implemented desktop and peer foundation

- Electron/React desktop shell with a narrow context-isolated preload bridge, tray lifecycle, preferences, local activity and mapping-management UI.
- Persistent Ed25519 device identity, signed LAN presence, two-sided pairing and pinned trusted peers.
- Short-lived authenticated encrypted peer requests using ephemeral X25519, HKDF, AES-256-GCM and the paired Ed25519 identity.
- Custom local and trusted-peer folder selection, mapping proposal/approval and a bounded development initial comparison.
- Capability-negotiated remote preview progress: remote scans have no time limit and report bounded authenticated counters for as long as they run; a closed connection or failed TCP keepalive ends the wait. Preview dialogs support cancellation, disconnected requests abort cooperative scan work, and older peers retain the single-response fallback. Progress alone does not lift the single-frame limit; chunked exchanges do, between updated peers.
- An explicitly initiated, direction-aware additive initial merge coordinated across both computers. Missing files transfer in 512 KiB encrypted requests with a full SHA-256 check and an atomic no-replace destination commit. Same-path differences are left untouched and surfaced.
- Initial merge rechecks each destination before adding a file: identical contents are accepted, and differing copies are preserved as conflicts without aborting unrelated transfers. The same check handles a file appearing at atomic commit. A file whose path is already a folder, symbolic link or other special entry on the receiving computer is left out and reported as a warning instead of stopping the merge or a continuous cycle; manifests carry these occupied paths as the optional `occupiedPaths` field, which older peers omit. Before the first copy, both computers' planned additions are checked against free disk space with 1 GiB kept spare (the peer side through `initial-merge-free-space-v1`), so a merge that cannot fit stops with the sizes involved instead of filling a disk; a source file removed or edited mid-merge is left out instead of aborting the remaining transfers, and final verification still gates activation. When verification finds files still on only one computer, the coordinator reruns both passes from fresh scans, up to three attempts, before stopping with a sample of the changing paths. Electron main reads and writes synchronized folders, staging files and the version archive through Electron's unpatched `original-fs`, so `.asar` files inside a mapping are scanned and copied as ordinary files. Case-only file aliases across Windows/Linux manifests are reported before copying and at final verification. Between computers that both advertise `directory-case-mapping-v1`, case-only directory aliases are resolved in the preview instead: the newest directory modification time selects the logical spelling, each computer keeps its own selected folder name, and the approved mapping routes every transfer, conflict, and restore path through that spelling. When the initial merge starts, each computer moves its approved older duplicate folders (with their contents) to the OS Trash or Recycle Bin after re-verifying their identity; a changed, symlinked, or nested-mapping folder is preserved and the merge stops. Older peers keep the collision report.
- Folder settings can be edited after setup (name, direction, ignore rules, version history), before or after the initial merge. Edits never widen what the other computer shares; see `17-SECURE-PEER-SESSION-AND-MAPPING.md`. Continuous reconciliation skips newly ignored paths and keeps their baselines, so the folder's file count still includes them.
- New-folder ignore rules include editable `.venv/` and `node_modules/` defaults and additive Common, Coding, JavaScript/TypeScript, Python, Rust and .NET presets. Presets do not change already-approved mappings.
- Automatic post-merge reconciliation. Both participants debounce native change notifications (one recursive watcher on Windows and macOS; on Linux one watcher per included directory, with no directory cap and ignore rules compiled once per walk; events for ignored paths and Tethera's own staging files are dropped on every platform, and a created, removed or moved folder on Linux re-walks only that folder instead of the whole tree; a refused or dropped watch degrades to the periodic scan and is retried). A check started only by file changes waits three times as long as the previous check took, up to two minutes, so a very large folder that never stops changing is not rescanned back to back; user actions and unfinished queued copies start a check straight away, the non-coordinator reports changes over the authenticated peer session, a five-minute full scan covers missed/coalesced notifications, and one deterministic mapping participant coordinates each cycle.
- Concurrent full-integrity scanning and a durable per-folder digest cache. Scans inspect up to 16 files at once while committing results in walk order, so manifests, counters and truncation are identical to a sequential scan. Continuous-sync scans on both computers skip reading files whose exact identity (device, inode, size, mtime and ctime in nanoseconds) matches an earlier settled digest; the first sweep after launch and one sweep per day re-hash everything. Reuse requires a usable identity on both sides (non-zero device and file id, positive nanosecond timestamps). On Linux it is disabled per root for FAT/exFAT by filesystem magic; on Windows the root gate is skipped because `statfs().type` is not meaningful there and the per-file gate rejects the zeroed file ids those filesystems report. A miss is never treated as a hit, and the same gate applies to the setup seed store and to transfer-recorded identities.
- Chunked peer exchanges. Between computers that both advertise `chunked-frames-v1`, manifests and observations larger than one 16 MiB frame travel as authenticated chunks (up to 256 MiB of JSON per exchange), so folder previews, initial merges, merge verification and continuous sync are no longer capped by a single frame. Older peers keep the legacy single-frame limits. Frame decryption requires full 16-byte GCM tags and 12-byte IVs.
- No scan file-count limit. Scans always include the whole folder and the Scan file limit setting is gone; a persisted value from an older version is dropped when settings load. The Rust engine accepts up to 1,000,000 files per side in one reconcile (250,000 per side took about 4 s in an opt-in release timing against an in-memory database), and a peer's file or operation list is bounded at 1,000,000 entries. A sync check is still bounded by the 256 MiB chunked exchange between updated peers (roughly 850,000 files per side) or the legacy 16 MiB frame with an older peer. A truncated scan, which only an older Tethera still produces at its own scan-file limit, fails closed with a request to update. Large engine requests are written to the engine pipe in pieces, and peer chunks are sealed from a streamed serialisation measured in a first pass and verified in the second, so neither message is built as one string; at 250,000 files per side this removed about 75 MB (engine) and 100 MB (peer) of held memory per changed cycle. On the manifest path, each side's file list and a received peer list are still held in full; the generation path does not hold either.
- Idle continuous cycles stop after scanning. Between computers that both advertise `continuous-fingerprint-v1`, a cycle whose order-independent observation fingerprints (computed with a streaming scan that holds no file list) match the last reconcile that queued nothing ends without exchanging manifests, reconciling or writing sync state. The first cycle after launch and one per hour always reconcile in full.
- Staged-generation continuous cycles. Between computers that both advertise `scan-generations-v1` and with no conflict choice pending, a changed cycle stages each computer's own full-integrity scan into SQLite as a sealed generation, fetches the other's sealed generation page by page (1,000 entries and 1 MiB per page, with backpressure and cancellation), stages that too, and reconciles the two generations set-based, so neither side builds or exchanges a full file list. Ignore rules apply at planning and occupied destinations are reported instead of queued. Generations are named, bound to the mapping revision, participant and root, and released by their owner once the exchange finishes; aborted and expired leftovers are cleaned after a failed cycle, and every staged generation is purged once at engine start, when nothing can be in flight, so an unfinished row left by a crash cannot hold the open-generation quota. A quiet fingerprint cycle still runs first and can reuse the peer's staged generation; a cycle holding a durable operation for a path that is still an open conflict — which only a user's conflict choice produces — stays on the manifest path, which owns replay and mirroring that choice, while ordinary queued work stays on the generation path; and a peer without the capability keeps the full-manifest path unchanged. Legacy peers keep working, and the legacy 16 MiB/256 MiB exchange limits still apply to that path. Staging and generation reconciliation scale with differences: at 250,000 files per side, a release-mode storage measurement (`cargo test -p sync-storage --release -- --ignored --nocapture generation_scale`, file-backed WAL database) stages one generation in 5-9 s (up to 30 s when the machine was under load; 26 s on the machine load observed for the version-11 measurement) and reconciles in about 0.8 s, whether nothing or 1,000 paths changed (1.5 s on the load observed for the version-11 measurement); the first reconciliation that records every baseline took 0.8-3.6 s, and a round with 1,000 one-sided additions whose destinations are occupied reconciled in about 1.6 s and reported every occupied path. These numbers come from one Linux development machine, not the packaged engine over RPC, and the wired desktop path over Electron has not been measured.
- Staged-generation initial merge. Between computers that both advertise `initial-merge-generations-v1` (and `scan-generations-v1`), each merge pass stages both computers' full-integrity scans as sealed generations and plans one direction at a time with `fileSync.planAdditiveGenerations`: the plan is read-only, pages over raw difference rows (the desktop requests 500 rows per page, keyset paged by path), reports one-sided pull candidates, same-path conflicts and occupied destinations, and never writes a baseline, queues an operation or records a conflict. Its first page carries exact whole-plan totals, so the free-space check, the case-only alias check (reported only when one of the two computers is Windows) and the peer's inverse-pass capacity estimate all run before either computer copies anything; a blocked destination path is left out of the plan and a blocked directory covers its subtree. The peer reports its bounded inaccessible-path detail list with its staged scan, so the coordinator reviews both computers' items together; the coordinator passes the accepted report's signature to the peer's inverse pass, which proceeds only while its fresh scan matches that exact report and stops for review when items changed. Both merge passes, the retry after files change mid-copy, and the two-sided convergence check use the same plan; the convergence check fails when either direction still has a pull candidate. A peer without the capability keeps the full-manifest merge unchanged. At 250,000 one-sided additions (500,000 difference rows) with 1,000-row pages in an opt-in release-mode storage measurement (`cargo test -p sync-storage --release -- --ignored --nocapture additive_plan_scale_timing`), the first page plus its whole-plan totals took about 1.4-2.7 s and paging the remaining 499 pages took about 1.6-2.8 s depending on machine load, with memory following one page rather than the plan. An initial merge with more than 10,000 unreadable paths on the generation path fails closed with a request to fix access or add ignore rules; the manifest path is unchanged. These numbers come from one Linux development machine, not the packaged engine over RPC, and the wired merge over Electron has not been run between two computers.
- Rust/SQLite verified-file baselines, durable retry operations, and explicit non-destructive conflicts. Only a one-sided change from a common digest may replace an existing file.
- A Recovery screen that projects durable conflicts and replacement-journal failures without exposing archive roots or internal object keys. For conflicts with two present copies, it freshly hashes both computers and either lets the user select one exact version or queues the strictly newer modified copy in bounded transactional batches. Ties, unavailable or changed copies, and direction-blocked choices remain unresolved. The visible list is paged in 100-row increments so a large conflict set does not create thousands of renderer rows at once.
- Updating a paired computer from this one. Each paired device card shows the other computer's Tethera version and, when it is behind this computer or has found a newer release itself, offers to update it. The other computer downloads the newest release from its own update feed and, on Windows and AppImage installs, restarts to install it; Linux `.deb`, `.rpm` and pacman installs download and wait for someone at that computer to approve the install, because their password prompt would block Tethera. Progress (checking, download percentage, restarting) and failures show on the card and in the activity log. Both computers need this version before one can update the other. See `17-SECURE-PEER-SESSION-AND-MAPPING.md`. The flow is covered by unit tests; it has not yet been run between two installed builds.
- Version history retention. When the mapping store becomes ready and then every hour, each computer applies an active folder's history limits to its own archive: a completed or aborted replacement leaves once it is older than the folder's day limit, or once newer versions (each distinct archived content counted once) already fill its storage cap, oldest first. A zero limit disables that dimension. Unfinished replacements, the source of an unfinished restore, and content that a remaining or unfinished journal entry needs are never removed.

## Authoritative Rust/SQLite mapping index

SQLite is the sole authoritative store for approved folder-mapping configuration. The desktop starts its stable device identity, opens the authenticated Rust RPC session, completes or verifies the legacy import, and then obtains active mappings through `mapping.list`. It never silently falls back to `state.json`.

Schema version 11 keeps the original migrations and adds:

- `mapping_revisions` for the current active event metadata;
- `mapping_tombstones` for durable deletion evidence;
- `mapping_delivery_outbox` for exact peer delivery and acknowledgement; and
- `mapping_legacy_import` for durable one-time import status.
- `file_sync_mapping_state` for the first verified observation boundary;
- `file_sync_baselines` for common SHA-256 file versions;
- `file_sync_operations` for retryable pull/push work; and
- `file_sync_conflicts` for simultaneous changes, one-sided deletion, direction mismatch, or unbased state.
- `archive_objects` for verified content-addressed archive metadata; and
- `file_replacement_journal` for restart-safe replacement and restore lifecycle state.
- `scan_generations` and `scan_entries` (version 6, entries clustered in version 10, entry `kind` added in version 11) for bounded staged scan generations with participant/revision/root/rules/hash-mode binding, file and occupied-path entries, idempotent incremental batches, seal verification, ordered paging, release in any state, quota/expiry, and cleanup;
- `scan_digest_cache` (version 7) for the derived per-folder scan digest cache;
- `directory_cleanup` (version 8) for approved case-duplicate folder cleanup evidence;
- `archive_object_deletions` (version 9) for archive objects whose files version history retention still has to remove; and
- `fileSync.reconcileGenerations` (with the mapping's ignore rules applied and occupied destinations reported), `fileSync.operationsPage`, `fileSync.conflictsPage`, and `scanGeneration.begin/append/seal/abort/readPage/release/cleanup` RPC.

Each migration step and each mapping mutation is transactional. A startup write probe distinguishes a genuinely writable store from a WAL database that can be opened for reads while another writer holds it. A newer schema is refused without modification.

`TETHERA_DATA_DIR` is the preferred engine data-directory variable. `FOLDERSYNC_DATA_DIR` remains a deprecated fallback and logs a warning when used. The desktop deliberately continues to pass Electron's existing `app.getPath("userData")`, so an installed `mappings.sqlite3` is not stranded by the naming cleanup.

## Active events, tombstones and pending delivery

Every active mapping has a positive monotonic revision, immutable event ID and author device. A local update requires the exact current revision. Removal transactionally writes a tombstone, removes the active projection and enqueues the tombstone for the other participant.

A tombstone contains the mapping ID, deletion event and revision, deletion and creation timestamps, deleting device, last-known active revision, and both mapping participants. Tombstoned IDs are terminal in this version: an active event with that ID can never revive it, regardless of arrival order. Re-adding the same folders creates a new mapping ID. Tombstones are durable and are not automatically pruned.

Active and tombstone events travel through the existing authenticated peer channel. The engine verifies that the authenticated peer, local device and event author are the mapping participants. Duplicate deliveries are idempotent; out-of-order events are resolved by revision plus event ID rather than wall-clock time. An outbox row is cleared only when the authenticated peer returns the exact mapping ID, event ID and revision. Disconnects leave it pending for retry.

This channel reconciles configuration only. It never scans a mapping or reads, writes, renames, moves or deletes a user file.

## One-time `state.json` migration

Legacy mapping fields are imported only while SQLite reports that legacy import has not completed. The desktop validates the entire intended set, rejects duplicate IDs, writes a mapping-only backup, verifies that backup, and sends one transactional import to the engine. Stable IDs, approved local/remote paths, modes, ignore rules, history limits, pending-delivery state and valid timestamps are preserved.

The completion marker commits in the same database transaction as the intended records and any tombstones needed to retire stale version-1 rows. A matching retry is idempotent. A different legacy snapshot cannot overwrite a completed import.

After the desktop reads the records back and verifies the exact intended configuration, it removes only SQLite-owned mapping fields from `state.json`. Unrelated preferences and temporary pending/rejected proposal UI state remain. A crash after database commit but before JSON cleanup repeats verification and cleanup on restart; it does not import again. The verified backup contains only mapping configuration, never identities, private keys, secrets or user-file contents.

Fresh installs and readable zero-mapping states commit an empty completed import. Missing JSON is treated as a fresh install. Malformed, duplicate or unreadable JSON fails closed and records a migration failure. A locked, unavailable or newer-schema database is not interpreted as zero mappings and is never rebuilt from JSON.

## Renderer and degraded behaviour

The renderer shows initial loading, ready, unavailable, unsupported/newer-schema, migration-required and migration-failed states. Active rows come from `mapping.list`; tombstones are never rendered as active. Pending configuration delivery is visible without presenting it as lost.

When the mapping store is not ready, the last in-memory view is not replaced with an empty list, mapping mutations are disabled, and a concise warning offers a safe engine retry. Settings show schema and migration status; journal mode is confined to advanced details. Diagnostics omit private keys and avoid unnecessary full database or mapping paths.

Creation, approval, pause/setup updates and removal are shown as durable only after their SQLite transaction succeeds. `state.json` no longer has a writable approved-mapping projection or one-way write-through reconciliation helpers.

## Local RPC boundary

Renderer access remains `renderer -> preload -> Electron main -> authenticated Rust stdio RPC`. The mapping methods are typed, reject unknown fields and require the engine session token before dispatch:

- `mapping.list`, `mapping.get` and `mapping.listPendingDelivery`;
- `mapping.upsert` and `mapping.remove`;
- `mapping.applyRemote` and `mapping.acknowledgeDelivery`; and
- `mapping.getMigrationStatus`, `mapping.importLegacy` and `mapping.recordMigrationFailure`.
- `fileSync.reconcile`, `fileSync.getState`, `fileSync.resolveConflict`, `fileSync.authorizeApply`, `fileSync.complete`, `fileSync.applyVerified` and `fileSync.fail`; and
- the read-only `archive.listVersions`, which is mapping-scoped and takes an optional positive `limit`; and
- `archive.listPrunable`, `archive.prune`, `archive.listObjectDeletions` and `archive.completeObjectDeletion` for version history retention.

The RPC exposes no SQL, no arbitrary file operation and no identity private key.

## Initial merge and continuous synchronization

Desktop comparison previews report time-throttled local listing, metadata and hashing activity, the current relative path, checked files, excluded/unreadable entries, bytes hashed and reused unchanged files. Unreadable files and directories are additionally reported per relative path with a short reason and a true total (bounded detail list), carried through the proposal to the approval dialog and persisted with the verified comparison through Rust/SQLite and peer delivery. Changed issue details require review even when aggregate file counts match. Both computers need a build whose engine accepts these additive preview fields; old previews without them remain readable. Remote preview scans report authenticated counters when both peers support `scan-progress-v1`, otherwise a waiting phase. Remote progress never includes paths or contents. Preview samples retain the 14 largest differences across the scanned manifests, ordered by size with path/category tie-breaks. Initial merges and sync cycles publish structured, never-persisted folder progress in the renderer snapshot: the three-step merge position, each computer's scan stage and counters (the local path only for this computer, remote counters only when the peer supports `scan-progress-v1`), and the file/byte position, rate and estimate while copying. Failures are carried separately from routine status, so a failed merge stays visible as an error after the peer goes offline. A reviewed comparison summary is cached for ten minutes under its operation, paths, peer, platforms, direction, mode and rules. Requesting approval reuses that summary without walking either folder again, including folders above 50,000 files. A responder refresh can likewise be reused for approval. Only eight summaries of at most 2 MiB each are retained, with no full manifests in this cache; a new or cancelled comparison cannot combine scans from different attempts. The reuse step is labelled explicitly. Independent responder consent and fresh pre-transfer/convergence checks still run. Settled file identities from setup scans are also kept in a bounded, short-lived seed store (root and rules keyed, local-user workflows only) so the consent and merge walks reuse digests for unchanged files and read only changed, new or above-ceiling files. A bounded in-process scan ledger records local manifest walks with their stage and reuse/hash counters. Console diagnostics report scan start, completion or cancellation/failure, elapsed time including queue wait, and manifest reuse/hash counters without paths or file contents. Explicit `**/node_modules/**` rules prune root and nested dependency directories before traversal. Read-only scans are cooperatively cancellable (preview cancellation/supersession, peer disconnect/deadline, pause/removal, shutdown, paired-scan sibling abort) with per-scan hash-buffer reuse and a process-wide budget of 4 active and 16 queued scans; peer frames stay capped at 16 MiB with a 32-message/4 MiB parked queue.

The preliminary Rust scanner, comparison and no-write plan are not wired into the live desktop transfer path. They still have documented development ceilings, use BLAKE3 rather than the desktop transfer path's SHA-256, and have no durable per-file index. Their opaque digest values must not be mixed with the desktop manifest contract.

The Electron main process owns the initial merge. One user action runs a full-integrity local pull, asks the authenticated peer to run the inverse pull, and performs a fresh two-sided convergence scan before activation. A deterministic device-id coordinator prevents simultaneous starts from deadlocking. Completion is reported only after the peer acknowledges the exact active mapping event. Each source file is hashed before transfer, read in bounded chunks only while its size and modification time remain stable, re-hashed at the destination, staged beside its destination, fsynced, and atomically linked into place without replacing a path that appeared after planning. Full-integrity scans are restricted to the approved mapping and its exact ignore rules. Initial-merge and verification scans use the mapping's durable digest cache (and the first merge walk also reuses the setup seed), and transferred files have their verified identity recorded, so these walks read only files that actually changed, are new, or exceed the preview hashing ceiling. The walk itself remains: per-file identity is the minimum sound freshness evidence, because directory timestamps cannot reveal a content edit. Truncated or digest-incomplete scans fail closed. Unreadable paths are listed for review: paths already acknowledged in the approved comparison are skipped without re-asking, new ones pause the merge until the user continues or cancels, and the held scan is reused for the merge. Skipped paths are excluded from the plan, are never treated as deletions, and are recorded in the structured outcome that survives restart. Differing files remain unchanged on both computers.

After activation, the lower participant device ID is the deterministic coordinator. Both participants watch their local tree; a non-coordinator change sends a bounded authenticated notification that queues the coordinator, while a five-minute full two-sided scan covers missed events. Full SHA-256 observations go to the Rust engine, which compares them with the last verified common baseline. A new path or one-sided modification permitted by the mapping mode becomes durable work. Both devices record the new baseline only after the destination verifies and atomically commits the exact source digest. A disconnect or restart leaves retry state in SQLite; a commit whose acknowledgement was lost converges on the next identical scan. Until the first two-sided scan replaces them, the initial merge's conflicts are shown as a pending check (syncing, or offline without the peer) rather than as conflicts needing attention, including when a mapping revision is acknowledged; skipped inaccessible items still need attention, and the non-coordinator shows its own scan counts while the coordinator reads its folder. Pausing asks for confirmation while folder work is running; the coordinator still refuses to pause during a running check.

Existing destinations are replaced only if their digest still matches the planner's expected destination digest. The new file is staged and verified beside the destination. The exact destination entry is then moved to a reserved same-directory displaced path, copied into `userData/version-archive/objects/sha256/<prefix>/<digest>`, fsynced, re-hashed, and recorded as `archived` in SQLite before the new file is installed with an atomic no-replace link. A path created concurrently in the installation or rollback window is never overwritten. Sync completion and the journal's `completed` transition commit together. Deterministic archive staging can be verified and published after restart, and every journal entry is bound to the canonical local root that created it. The reserved displaced inode is retained and ignored by scans because POSIX permits late writes through an already-open handle; retention removes it only when its journal entry is pruned and it still hashes to the archived digest. The external content-addressed object remains the authoritative archived version. New destinations use the same atomic no-replace link.

Startup processes incomplete replacement rows before watchers resume. An unchanged old live digest aborts work safely; the exact planned replacement plus a verified archive rolls forward; missing/corrupt archive content becomes `integrity-failed`; every ambiguous observation becomes `recovery-required`. Restore uses the same pipeline and archives a current live file before replacing it. A minimal Electron API exposes the engine-backed restore primitive, and replacement failures are visible in Recovery. Archived versions for one active folder can now be browsed and restored from the Recovery screen. The engine read is bounded to the most recent versions and reports when older history exists beyond that page. Main projects each journal row into a renderer-safe summary that deliberately omits archive roots, object keys and digests, so the renderer can identify a version by path, time, size and availability without learning where the archive lives. Retention prunes in restart-safe steps. The engine lists removable versions without changing anything. The desktop removes each version's `.tethera-displaced-*` copy only while it lies under the folder's current canonical root and still hashes to the archived digest; an edited copy is kept and reported. One engine transaction then re-evaluates the policy, deletes the journal rows, and moves every archive object that nothing references any more into `archive_object_deletions`. The desktop unlinks each queued object file before confirming it. Queued content cannot gain a new archive reference until its removal is confirmed, so an object file reused by a new replacement is never deleted underneath it. A pass finishes queued removals left by an interrupted pass first, and skips a folder whose root is unreachable. History of a removed folder is not pruned.

The first observation of a legacy/imported active mapping never assumes a one-sided file is new. Simultaneous modifications, one- or two-sided deletions, direction-blocked changes, and paths without a verified baseline become durable conflicts; files are not deleted and the folder/activity UI identifies affected paths. Legacy initial-merge conflict outcomes are promoted into the authoritative SQLite projection before their stale JSON copy is retired.

For a durable conflict where both files are present, the coordinator can inspect both copies through the authenticated peer session and queue one exact version as normal durable sync work. The renderer submits the device-bound digests and sizes it displayed; the coordinator freshly revalidates both copies before accepting that choice and replay validates them again. Each transfer acknowledgement names the exact mirrored durable operation. The receiving side authorizes every incoming file application against that exact pull operation; a missing operation is accepted only as a no-write retry when the verified baseline and live file already match. Restart preserves selected intent, but a changed or missing source/destination blocks it and forces reconciliation. Installation reuses the existing verified transfer and archive-backed replacement journal; each local conflict remains until exact completion is committed. An unresolved replacement recovery issue blocks reconciliation before scanning and its referenced operation cannot be deleted or rewritten by a later plan. One-way direction is enforced, and missing/deletion conflicts cannot be selected.

Conflicts whose two copies differ only in CRLF versus LF line endings are settled without the user. At the start of each coordinator cycle, and after a reconcile once the peer has observed it, the coordinator compares every unbased or simultaneous two-copy conflict it has not yet compared, asking the peer for a line-ending-insensitive text digest (see `docs/17-SECURE-PEER-SESSION-AND-MAPPING.md`), and queues the LF copy through the same exact-choice path as a user's choice; the next cycles apply the queue. The comparison record lives in memory, so it is repeated once after a restart and again whenever a copy changes; a comparison that fails is retried on a later cycle, and a queued choice that exhausts its retries is left to the user instead of being queued again. The activity log announces each conflict once, when it first needs the user: resolving part of a set re-announces nothing, a conflict whose choice is queued is not announced, and a line-ending candidate waits until the coordinator has compared it or a later pass still finds it, so a settled file never appears as a conflict left untouched.

## Clearly not implemented

- The comparison **preview** and the mapping-approval summary still exchange full manifests: the preview walks both folders, compares the two manifests and stores a bounded sample. The merge itself and its convergence check use staged generations between updated peers, but approving a mapping still holds each side's file list in memory while that comparison runs.
- Paged operation/conflict consumption at huge difference counts: `fileSync.operationsPage` and `fileSync.conflictsPage` exist, but a cycle and Recovery-state request still materialise their operation and conflict arrays. The Recovery screen limits rendered rows, but process memory still follows the number of differences in the folder, which is the generation design's goal, but not below it.
- Engine-owned filesystem watching/network transfer, resumable/content-defined chunking, or bandwidth scheduling.
- File deletion or rename propagation, resolving conflicts where either copy is missing, or pruning the archive history of removed folders.
- NAT traversal, cloud services, accounts or telemetry.
- Initial merges that leave more than 10,000 conflicts or skipped paths: the persisted outcome list is capped at 10,000 entries, so the coordinator refuses a larger pass result from the other computer; a staged-generation merge with more than 10,000 destination-blocked paths fails closed before planning.
- Code-signed/notarised release builds.

## Recommended next pull request

Page operation and conflict consumption for huge difference counts: `fileSync.operationsPage` and `fileSync.conflictsPage` exist, but a cycle and Recovery-state request still materialise their operation and conflict arrays, and the merge's paged plan still accumulates every same-path conflict and occupied path in memory. Driving those consumers page by page is the remaining step toward memory that follows the page rather than the difference count. Deletion and rename propagation should remain disabled until cross-platform interruption tests prove the archive recovery and retention lifecycle safe.
