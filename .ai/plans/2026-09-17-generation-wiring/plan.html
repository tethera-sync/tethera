Wire continuous reconciliation through sealed scan generations

created 2026-09-17 · status ready · target: crates/sync-storage, crates/sync-engine, apps/desktop/src/main

TL;DR

The engine already stages scans into SQLite (scan_generations/scan_entries) and reconciles two sealed generations set-based, but no production code stages or fetches a generation: the live continuous cycle still builds two full FileManifest objects in memory and exchanges them as one chunked message. Phase 1 wires the continuous reconciliation path onto generations between peers that both advertise scan-generations-v1, and closes three correctness gaps first (ignore rules, occupied-path skips, generation release). The initial merge and paged operation/conflict consumers are deliberately deferred to separate PRs. Deletion and rename propagation stay disabled.

1. Goal

Make steady-state continuous synchronization scale with the number of differences rather than the folder size, so a 250,000-file folder no longer materialises two full file lists per changed cycle, while preserving every current correctness guarantee: no user file is replaced without the existing verified staging/archive pipeline, newly ignored paths stay out of planning with their baselines, one-sided additions are never planned onto an occupied destination path, and older peers keep working unchanged.

2. Codebase Understanding

2.1 The live continuous cycle today (full manifests)

Everything below is in apps/desktop/src/main.

  • flushContinuousSync (index.ts:2584-2837) is the whole cycle; the deterministic coordinator is the lower device id (index.ts:1932-1938).
  • Cheap first pass: when both peers advertise continuous-fingerprint-v1 and the last quiet reconcile still matches, local runCachedFolderFingerprint (index.ts:622) plus a peer continuous-sync-scan with knownFingerprint can end the cycle with no lists at all (index.ts:2636-2650). This stays.
  • Otherwise the full pass builds both manifests: runCachedFolderScan (index.ts:611) and requestPeerManifest (index.ts:632) over runPairedScans (paired-scan.ts:10); the peer's continuous-sync-scan responder scans and returns a manifest (index.ts:4125-4160).
  • syncableObservations (continuous-sync.ts:191-209) filters one-sided files whose destination path is occupied by a folder, symlink or special entry, then both observation arrays go to the local engine fileSync.reconcile (index.ts:2732-2740) and to the peer as continuous-sync-observe (index.ts:2748, handler index.ts:4260-4293).
  • executeContinuousOperations (index.ts:2457-2564) drives both sides: pulls via pullPlannedFile (index.ts:2918) and pushes via continuous-sync-apply (index.ts:4294), authorizing every receive against the exact mirrored durable operation.
  • Memory: both FileManifest.files arrays are held for the whole cycle (index.ts:2655-2662, 2464); docs/15-IMPLEMENTATION-STATUS.md:113 records this as the known limit.

2.2 What already exists for generations

  • Storage: crates/sync-storage/src/scan_generations.rs — begin (110), append (232), seal (370), abort (426), read_page (516), cleanup (585); bound to mapping, authenticated participant, revision, root, ignore rules and hash mode; quotas 4 open generations / 1,000,000 entries / 1,000-entry batches; 24 h expiry.
  • Reconciliation: MappingStore::reconcile_generations (file_sync.rs:314) with the set-based planner plan_generations_reconciliation (file_sync.rs:1356): identical paths baseline inside SQLite, only differences stream out.
  • RPC: scanGeneration.begin/append/seal/abort/readPage/cleanup and fileSync.reconcileGenerations (crates/sync-engine/src/main.rs:326-337, method list 1718-1770).
  • Peer serving: scan-generation-read-page responder (index.ts:4164-4181) reads bounded pages through the engine; scan-generations-v1 is advertised (index.ts:4162).
  • Client half already written but unreferenced outside tests: fetchPeerGenerationPages (scan-generation.ts:172), streamRelativeFilePaths (212), entry/batch parsers (75-135), byte-bounded toEntryPages (138).
  • Scanner kernel that can drive staging without a manifest: scanFolderEntries (folder-manifest.ts:388) already supports digest-cache reuse, cancellation, activity counters, unreadable reporting and occupiedPaths; fingerprintFolder (folder-manifest.ts:602) is the existing no-list consumer.
  • Scale evidence: generation_scale (scan_generations.rs:1547) stages 250,000 entries in 5-9 s and reconciles in ~0.8 s (one Linux machine, file-backed WAL).

2.3 Blocking gaps found during this investigation

#GapEvidence
G1 Generation planning ignores the mapping's ignore rules. A baselined path that becomes ignored is missing from both staged scans, so it falls into the baseline-only branch and becomes a DeletionNotPropagated conflict. plan_reconciliation already handles this (file_sync.rs:861-865); the generation planner does not. docs/03-SYNC-SEMANTICS.md:100 ("Staged scan-generation reconciliation does not take rules yet"), file_sync.rs:1356-1462
G2 Staged observations carry no occupancy. syncableObservations currently keeps one-sided files off a destination path used by a folder, symlink, special entry, or an ancestor that is a synced file. Without that filter the generation planner would queue transfers that can only fail (atomic no-replace link / ensureContainedDestinationDirectory) and would retry them every cycle. continuous-sync.ts:191-209, folder-manifest.ts:1005-1036, commit 0122b0d
G3 Nothing removes a sealed generation. abort refuses a sealed generation (scan_generations.rs:453-457); cleanup deletes only aborted or expired rows. Wiring the cycle without a release step would accumulate ~tens of MB per cycle for 24 h. scan_generations.rs:370-424, 585-600
G4 The read-page gate requires the caller to be the elected coordinator (requireSharedActiveFolder, index.ts:3997-4007). A symmetric exchange (each side fetches the other's sealed generation) needs the non-coordinator to read a sealed generation of its own shared mapping. index.ts:4169, docs/17-SECURE-PEER-SESSION-AND-MAPPING.md:97
G5 No production code calls scanGeneration.begin/append/seal or fetchPeerGenerationPages; the peer responder is reachable over the wire but nothing initiates it. apps/desktop/tests/scan-generation.test.ts is the only caller.
G6 Staged entries cannot say "directory/special entry occupies this path", so the planner cannot reproduce the occupancy skip even in principle. scan_generations.rs:43-47 (path, size, digest only)

3. Recommendation

Do the continuous path now, as two sequenced PRs, and do not touch the initial merge or the operation/conflict paging in this pass.

  1. Phase 1A (Rust, first PR): close G1, G2, G6 and G3 in sync-storage/sync-engine with tests. Nothing in the desktop calls the new fields yet, so behaviour is unchanged; this matches the repository's existing pattern of landing generation contracts before wiring (docs/15-IMPLEMENTATION-STATUS.md:113).
  2. Phase 1B (desktop, second PR): stage, exchange, reconcile, release — capability-gated so peers without scan-generations-v1 keep today's manifest path byte for byte.
  3. Phase 2 (later PR): the initial merge. It cannot use reconcile_generations: that requires an active mapping (file_sync.rs:322) and writes baselines, while the merge runs at ready-for-initial-sync with additive, no-baseline semantics driven by computeSyncPlan (initial-sync.ts:229) and a paged to-pull plan the engine does not expose yet. Bundling it would put a new engine contract on the most safety-critical flow into the same review as the steady-state change.
  4. Phase 3 (later PR): paged operation/conflict consumers and UI aggregation. Both arrays are proportional to differences — exactly what the generation design already makes memory follow — so this is a real but secondary concern that needs renderer-contract changes.

Reasons to keep this scoped: the continuous cycle is the recurring cost and the one with the clearest existing contracts; the quiet-fingerprint path already handles the common idle case; and Phase 1A is independently testable without any desktop change.

Do not enable deletion propagation, rename propagation, or conflict winner selection. Nothing in this plan changes replacement, archive, retention, or recovery behaviour.

4. Scope

In scope

  • Schema v11: staged occupancy kind on scan_entries, with migration and validation.
  • Generation planner: ignore rules (G1), occupancy skips with faithful baselined/conflict behaviour (G2/G6).
  • scanGeneration.release plus desktop release/cleanup wiring (G3).
  • Desktop staging (local and incoming), capability-gated cycle, two new peer requests, participant-scoped page reading (G4), progress and occupied-path reporting.
  • Tests, docs updates, and the compatibility fallback.

Out of scope

  • Initial merge / comparison preview changes (Phase 2).
  • Engine RPC response reshaping, fileSync.operationsPage/conflictsPage consumers, renderer conflict aggregation (Phase 3).
  • Any change to transfer, staging-write, archive, retention, recovery or conflict-resolution semantics.
  • Deletion/rename propagation; NAT traversal; accounts.
  • Retiring the legacy manifest path — it stays for older peers permanently until a later cleanup.
  • New dependencies, new lockfiles, unrelated refactors.

6. Implementation Plan

Phase 1A — Rust contracts (PR 1)

  1. Schema v11: staged occupancy kind. In crates/sync-storage/src/mapping.rs: bump SCHEMA_VERSION to 11 and add migrate_v10_to_v11 following the existing step pattern. Add kind TEXT NOT NULL DEFAULT 'file' CHECK (kind IN ('file','directory','special')) to scan_entries (an ALTER TABLE is sufficient here; rebuilding as in v10 is acceptable but not required). Existing staged rows become file. Update the v10 rebuild's CREATE TABLE in migrate_v9_to_v10 only if the executor wants a single canonical table definition; the migration chain is additive, so either way each step must be self-contained.
  2. Entry kind through staging, paging and validation. In scan_generations.rs:
    • GenerationEntry gains #[serde(default = "default_kind")] pub kind: String with "file" as the default, mirroring the existing stringly-typed hash_mode style.
    • validate_generation_entry: accept only file|directory|special; a file entry keeps the current size/digest rules; a directory/special entry must have size == 0 and digest.is_none() (fail closed rather than ignore).
    • append_scan_batch: insert kind; include kind in stored_entries/stored_matches_entry so a replayed batch with a changed kind is rejected exactly like a changed digest.
    • read_generation_page: select and return kind; keyset ordering by relative_path is unchanged.
    • seal/status/quota counting: unchanged (all rows count).
  3. Ignore rules in generation reconciliation (G1). Add #[serde(default)] pub ignore_patterns: Vec<String> to ReconcileGenerationsRequest (file_sync.rs:141), validated by the same rules the full-array request uses (reuse validate_reconcile_request's pattern checks; do not duplicate the matcher). In plan_generations_reconciliation, build IgnoredPaths (file_sync.rs:1260) and skip any streamed row whose path it contains — mirroring plan_reconciliation file_sync.rs:861-865. Identical pairs still advance baselines via advance_identical_generation_baselines (file_sync.rs:1491), so an ignored-but-identical path is harmless. Update docs/03-SYNC-SEMANTICS.md:100.
  4. Occupancy-aware planning and reporting (G2/G6). File rows and occupied rows share scan_entries. In plan_generations_reconciliation:
    • Restrict the identical-pair baselining SQL to local.kind = 'file' AND remote.kind = 'file' so an occupied row can never advance a baseline.
    • Build the differences stream from kind = 'file' rows only for files; occupied rows participate as blockers, not as observations.
    • When a row is a one-sided file addition, probe the destination generation for the path itself and each ancestor with a prepared point lookup (SELECT kind FROM scan_entries WHERE generation_id = ?1 AND relative_path = ?2). Any hit blocks the addition: a directory/special ancestor is occupancy, and a file ancestor is the structural file-versus-folder conflict that createDestinationOccupancyCheck also treats as blocking (folder-manifest.ts:1005-1036).
    • Blocked outcome must mirror today exactly: with no baseline for that path, report it as an occupied skip (no operation, no conflict — safe to re-plan if the user renames something); with a baseline, plan DeletionNotPropagated as today's filtered-observation path does (the destination no longer lists the path and neither does the source view reach the planner).
    • Divergent pairs (both sides present, different digests) are unaffected: occupancy never applies to a path present on both sides.
    • Add occupied_paths: Vec<String> to the generation reconcile result (serialised only when non-empty) so the desktop can keep calling recordOccupiedPaths. Keep it proportional to blocked additions, consistent with today's list.
  5. Release (G3). Add release_scan_generation(&self, generation_id: &str) to scan_generations.rs: one transaction that deletes the generation row in any state (open, sealed, aborted) with its entries cascading, and returns NotFound for an unknown id. Expose scanGeneration.release through crates/sync-engine/src/main.rs (handler near the other generation handlers, add to the token-required method list at 1718-1770). Leave cleanup and abort semantics as they are; update docs/06-DATA-MODEL.md, docs/09-LOCAL-RPC.md.
  6. Rust tests. Extend the existing suites rather than adding new harnesses:
    • scan_generations.rs: kind round-trip through append/read-page; kind mismatch on replay rejected; occupied validation (non-zero size or digest rejected); release deletes sealed + open + entries, missing id is NotFound; v10→v11 migration preserves staged rows as file (follow the existing migration test style at mapping.rs:2973).
    • file_sync.rs: generation planning equivalence with full-array planning under (a) newly ignored paths — no conflict, baseline retained, and removal of the rule re-compares against the baseline; (b) occupied directory/special at the exact path and as an ancestor; (c) a file ancestor; (d) baselined path whose destination became occupied still conflicts; (e) divergent pairs unaffected. Follow generations_reconcile_to_the_same_outcome_as_full_arrays (scan_generations.rs:929) and set_based_generation_planning_matches_full_array_planning (1048).
    • Extend generation_scale (scan_generations.rs:1547) to include occupied rows so the ancestor-probe cost is measured, and record the numbers in docs/15.

Phase 1B — Desktop wiring (PR 2)

  1. Streaming scan sink. In folder-manifest.ts:
    • Allow onEntry to return void | Promise<void> and await it at the call site (folder-manifest.ts:523). Existing callers pass sync functions and are unchanged.
    • Add onOccupied?: (occupied: OccupiedPath) => void to the scan options so the staging consumer sees occupied records as they are discovered (the kernel already yields them at folder-manifest.ts:325 and :330). scanFolder/fingerprintFolder keep collecting into the summary.
    • Add an exported batching helper (e.g. stageFolderEntries) that mirrors scanFolder but flushes at most SCAN_STAGE_BATCH_ENTRIES = 1_000 entries to an async sink, awaiting each flush before continuing (backpressure), and returns the existing ScanSummary. Do not change scanFolder behaviour.
  2. Generation staging module. New apps/desktop/src/main/generation-staging.ts (keep scan-generation.ts as the pure contract/validator module it documents itself to be at scan-generation.ts:7-11):
    • stageLocalGeneration(folder, mappingRevision, signal, onActivity): scanGeneration.begin with { generationId: randomUUID(), mappingId, participantDeviceId: localId, mappingRevision, root: folder.localPath, ignorePatterns, hashMode: "full-sha256" }, then the streaming sink appends batches with strictly increasing sequence (files and occupied entries share the batch and the 1,000 cap), then seal with the exact expected count. Run it through withFolderDigestCache and runAdmittedScan so digest reuse, the scan ledger, admission limits and cancellation behave exactly like runCachedFolderScan (index.ts:545-625). On any failure call scanGeneration.abort (best effort) and rethrow.
    • stageIncomingGeneration(folder, peerDeviceId, peerRoot, generationId, signal): begin with the peer as participant, then iterate fetchPeerGenerationPages (scan-generation.ts:172) and append batches, then seal; abort on failure. Implement the missing PeerPageClient: request over requirePeerSessions().request with NO_PEER_RESPONSE_DEADLINE, supportsGenerations over cachedPeerCapabilities.
    • releaseGeneration(generationId) wrapping scanGeneration.release (best effort, log-only failures).
    • Both stagers return { generationId, entries, occupied, ignored, unreadable, unreadableEntries, rootPath }; nothing holds a file list.
  3. Capability-gated cycle. In flushContinuousSync (index.ts:2584), keep the durable preflight, quiet-fingerprint pass, execution, projection and error handling shared, and branch only the scan/reconcile exchange: 
    const generations = capabilities.has(SCAN_GENERATION_CAPABILITY)
if (generations) await runGenerationCycle(folder, peer, observedAt, chunked, signal?)
else await runManifestCycle(folder, peer, observedAt, chunked, knownPeerManifest)
    Generation cycle steps:
    1. runPairedScans of stageLocalGeneration and a new requestPeerGenerationScan (continuous-sync-generation-scan, below). Report local staging counters through reportScanCounts(folderId, "changes", { local }) exactly as today, and peer counters as { remote } when the reply carries them.
    2. stageIncomingGeneration for the peer's sealed generation.
    3. fileSync.reconcileGenerations with { mappingId, localGenerationId, remoteGenerationId, mode: folder.mode, observedAt, queueOperations: true, ignorePatterns: folder.ignorePatterns }.
    4. recordOccupiedPaths(folder, result.occupiedPaths ?? []) then the existing conflict/state projection (retireInitialConflictProjection, applyFileSyncStateToFolder, recordContinuousConflicts, broadcast) — unchanged.
    5. Peer reconcile: new continuous-sync-observe-generations request carrying { folderId, localGenerationId, remoteGenerationId (the peer's own, echoed), mode: invertMode(folder.mode), observedAt }. The reply is the peer's reconcile state; validate operations with parsePeerFileOperations (ipc-validation.ts:479) and conflicts/recovery with strict parsers.
    6. executeContinuousOperations (index.ts:2457) unchanged in behaviour. Its remoteManifest parameter must become a source resolver: for the manifest path keep today's remoteFilesByPath map; for the generation path resolve { size: operation.sourceSize, digest: operation.sourceDigest } from the durable operation, because validateTransferDescriptor compares only size and digest (ipc-validation.ts:377-389) and pull-file-descriptor re-verifies the live peer file. The mirrored-operation check (continuous-sync.ts:250-262) and every completion/failure path stay exactly as they are.
    7. Release the two generations after reconcile succeeds; release in finally on failure. If the peer never receives the observe request, its own generations stay until cleanup expiry.
  4. New peer requests and gates. In handlePeerRequest (index.ts:4053-4647):
    • continuous-sync-generation-scan: requireSharedActiveFolder + withPeerFileOperation; stage the responder's own generation with the digest cache and reportScanCounts(folderId, "peer-changes", …); reply { generationId, entries, occupied, ignored, unreadable }. Keep continuous-sync-scan (index.ts:4125) byte-for-byte for older callers.
    • continuous-sync-observe-generations: requireMappingMutations + requireSharedActiveFolder; require request.mode === folder.mode and use folder.ignorePatterns (never peer-supplied rules) exactly as the existing observe handler does (index.ts:4260-4275); stage the incoming generation from the coordinator, reconcile, project state, and reply it. Release the incoming generation and the echoed remoteGenerationId in finally.
    • scan-generation-read-page (index.ts:4164): replace requireSharedActiveFolder with a new participant-scoped gate — active mapping, not blocked, not paused, folder.remoteDeviceId === context.peerId — and keep every other bound. Update docs/17-SECURE-PEER-SESSION-AND-MAPPING.md to say both authenticated participants may read a sealed generation of their shared mapping, bounded by pages and expiry; scans are still coordinator-initiated only.
  5. Validation and parsers. scan-generation.ts: parseGenerationEntry accepts kind (file default; unknown rejected). Add strict parsers for the generation scan reply and the observe-generations reply using the existing validation conventions; bound counters and lists; reject unknown shapes before they affect local state.
  6. Cleanup wiring. Call scanGeneration.cleanup with the current timestamp once when the engine becomes ready and after generation-cycle failures, so crash leftovers expire. Do not call it mid-cycle.
  7. Fallback and compatibility. The generation path is used only when this build supports it and the peer advertises scan-generations-v1. Otherwise the manifest path runs unchanged, including assertManifestFitsExchange and the legacy byte budgets. No engine response shape changes (the generation result only gains an optional field), so older desktops remain compatible.

  • Reuse IgnoredPaths, scanFolderEntries, withFolderDigestCache, runAdmittedScan, runPairedScans, fetchPeerGenerationPages, parsePeerFileOperations and the existing validation helpers before writing anything new.

9. Acceptance Criteria

  1. Between two updated peers, a full continuous cycle stages, exchanges, reconciles and releases generations; no FileManifest with a full file list is built on that path (assert in tests; check with the TETHERA_SCAN_STRESS harness if convenient).
  2. A peer without scan-generations-v1, or a build without local support, runs the existing manifest path unchanged and passes the existing suite.
  3. Newly ignored baselined paths produce no conflicts and keep baselines; removing the rule re-compares against the baseline (Rust test).
  4. One-sided additions onto an occupied path (exact, directory/special ancestor, or file ancestor) are skipped and reported; a baselined path whose destination became occupied still conflicts — both matching today's manifest behaviour.
  5. Generations in every state can be released; a normal cycle leaves none behind; crash leftovers are removed by cleanup after expiry.
  6. Schema v11 migrates an existing v10 store with staged rows preserved, and refuses a newer schema without modification.
  7. No deletion or rename propagation, no change to replacement/archive/retention/recovery, and no secrets or full paths exposed to the renderer or peer logs.
  8. All commands in section 8 pass, and docs/15-IMPLEMENTATION-STATUS.md accurately separates implemented from planned.

10. Risks and Notes

  • Ancestor-probe cost: the occupancy check costs one point lookup per ancestor per one-sided addition; pathological all-new trees are measured by the extended generation_scale. If it proves material, cache per batch or hoist a depth-bounded join — do not drop the check.
  • Authorization change (G4): letting a non-coordinator read a sealed generation of its own mapping is a deliberate, bounded widening of scan-generation-read-page; it must be reviewed and covered by a test that a non-participant peer is still rejected. If reviewers reject it, the fallback design is coordinator-pushed batch staging of its own entries, which keeps the gate untouched at the cost of a new batch request type.
  • Nested peer requests: the peer's observe handler makes page requests back to the coordinator while the coordinator awaits the observe response. Each request opens its own connection (peer-session-service.ts:212), and withPeerFileOperation is a per-(peer, folder) guard that throws on overlap, not a queue — the plan must ensure no side holds that lock while awaiting the other (the coordinator's outbound observe is not wrapped). Test the handler path with a stalled page fetch.
  • Generation churn: each full cycle stages two generations per side plus two incoming copies; release-on-success keeps disk bounded, but verify with the quota (4 open per mapping) that failure paths cannot exhaust it.
  • Incoming-generation abort: a dropped connection must abort the incoming generation, not leave it open until expiry; the handler's finally owns this.
  • Peak memory is reduced but not flat: operations, conflicts and recovery issues still arrive as arrays; that is Phase 3, and the plan should say so rather than implying the limit is gone.
  • Compatibility: old peers keep manifests, so both code paths must stay healthy and tested until the platform matrix justifies retiring the legacy path.
